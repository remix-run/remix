Fix server-rendered `<Frame>` streams continuing to run after the render stopped. When `resolveFrame` returns a stream and the stream returned by `renderToStream()` is cancelled, its `signal` aborts, or a blocking frame fails, the frame stream was left open, so the work producing it, such as an internal frame request, kept running. This happened whether the frame was still producing its first chunk, waiting behind a sibling frame, or resolved after cancellation. The frame stream is now cancelled with the cancellation reason or the render error, and a frame stream that errors is released instead of staying locked. A render whose `signal` is already aborted no longer calls `resolveFrame`.
